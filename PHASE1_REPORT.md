## 2. Findings reproduced, root cause, and fix

### Finding 1 — Unknown hospital issuers caused false merges

**Reproduced**: `identity.build_candidate_features` (then in
`identity/__init__.py`) assigned a single hardcoded fallback issuer,
`"BATCH_DEFAULT_SOURCE"`, to every record lacking an explicit
`identifier.system`/facility field, **regardless of which file it came
from**. Two independently-sourced CSVs with no facility column and the same
local UHID value became ACCEPTED members of one cluster.

A second, related bug: the structured-identifier branch of
`detect.detect_in_text` assigned issuer `"NATIONAL"` to a national scheme
(Aadhaar/ABHA) detected in a *structured* field, while the free-text
identifier detectors (`detect.identifiers`) assigned `"UIDAI"`/`"ABDM"` for
the *same* scheme detected in free text — the same national ID, structured
vs. free text, would never scope-match.

**Fix**:
- `config.AppConfig.source_system_map: tuple[tuple[str, str], ...]` — an
  explicit, ordered `(path_prefix, issuer)` mapping, longest-prefix-wins
  (`config.resolve_configured_issuer`). Exposed on the `analyze` CLI as
  repeatable `--source-system PATH_PREFIX=ISSUER`.
- `identity.build_candidate_features`'s fallback-issuer priority is now:
  (1) an explicit issuer the format itself carries (FHIR
  `identifier.system`, or a fixed national scheme) — unchanged, highest
  priority; (2) an explicit `FACILITY_NAME` field in the record; (3) the
  configured `source_system_map` for that file's path; (4) **a
  per-file-scoped `UNKNOWN_SOURCE:<path>` fallback** — never shared across
  files by default. Rows within one file still share scope naturally
  (same declared source).
- `detect.__init__._NATIONAL_ISSUERS = {"aadhaar": "UIDAI", "abha_number":
  "ABDM", "abha_address": "ABDM"}` replaces the inconsistent `"NATIONAL"`
  constant, matching the free-text route exactly.
- `schema.Field` gained optional `issuer`/`scheme` fields so an adapter that
  already knows the authoritative scope (FHIR) can hand it through
  `detect_in_text(..., pre_issuer=..., pre_scheme=...)` untouched, instead
  of the generic header-alias inference silently dropping it (this also
  fixes half of Finding 2 — see below).
- The dev/held-out fixture corpus's own declared source contract
  (`gate.phase1.DEV_SOURCE_SYSTEM_MAP`) now explicitly states that
  `arif_corroborated/` and `meera_corroborated/` are one hospital's
  fragments, and declares the new `source_scope_configured_shared`
  fixture pair as a deliberately shared issuer — this is the "update
  fixtures/configuration transparently" the task asked for; no patient
  evidence was invented, only the source-system *contract* was made
  explicit where the fixture already represented one hospital's records.

New fixtures (`tests/fixtures/dev/`, generated by `scripts/gen_fixtures.py`):
`source_scope_unknown/{hospitalA,hospitalB}` (unconfigured, must not merge),
`source_scope_configured_shared/{hospitalA,hospitalB}` (deliberately shared
issuer, must merge), `source_scope_configured_distinct/{hospitalA,hospitalB}`
(two configured, distinct issuers, must not merge), `aadhaar_consistency/`
(same Aadhaar value, structured CSV + free-text note, must merge).

### Finding 2 — FHIR references did not establish patient association

**Reproduced**: a Bundle with `Patient` + `Encounter.subject.reference`
reported the reference as `resolved: true`, but the Encounter never joined
the Patient's cluster — nothing in `plan.builder`/`identity` ever read a
FHIR reference to drive identity. Separately, `identifier.value` extracted
from a FHIR resource lost its `scheme`/`issuer` before reaching identity
resolution (`detect_in_text`'s structured branch inferred scheme from the
field's *path*, e.g. `"identifier.value"`, which never matches a header
alias — so FHIR identifiers silently never became scoped identity
evidence at all, independent of Finding 1).

**Fix**:
- `ingest.fhir_adapter.Reference` gained `field_key` (`"subject"` /
  `"encounter"` / `"performer"`) and `target_resource_no` (the resolved
  Bundle-entry ordinal it points at, once resolved).
- `FhirResource` gained `patient_subject_resource_no` and
  `patient_subject_ambiguous`. Computed strictly from `field_key ==
  "subject"` references that resolved to an actual `Patient` resource type
  (never `performer`/`encounter`, so a Practitioner reference can never
  establish a patient-identity merge); more than one distinct resolved
  Patient target is flagged `patient_subject_ambiguous` and never picked
  arbitrarily.
- `plan.builder.run_pipeline` turns a resolved `patient_subject_resource_no`
  into a direct `resolver.attach_exact(record, patient_record,
  "FHIR_SUBJECT_REFERENCE")` edge (going through the same contradiction-veto
  union-find as every other exact edge), and an ambiguous one into an
  explicit `resolver.flag_held(record, "FHIR_SUBJECT_REFERENCE_AMBIGUOUS")`
  (new `ClusterResolver` method) rather than a silent no-op.
- `ingest.fhir_adapter._extract_resource`'s identifier loop now sets
  `Field.issuer`/`Field.scheme` directly from `identifier.system` (or a
  generic `"fhir_identifier"` scheme when absent, so it still falls through
  Finding 1's normal conservative fallback instead of being dropped).

New fixtures: `fhir_patient_link/{two_patients_bundle,
performer_not_patient, ambiguous_subject_bundle,
duplicate_logical_id_bundle}.json`.

### Finding 3 — Contained references resolved against the wrong owner

**Reproduced**: `parse_fhir` built one Bundle-wide `contained_scope_ids:
set[str]`, so Observation A's `#elsewhere` reference resolved to `True`
merely because *some other resource* (Encounter B) happened to contain an
id `"elsewhere"`.

**Fix**: `contained_by_owner: dict[resource_no, dict[id, count]]` is now
keyed by the **owning resource's own** `resource_no`; a `#id` reference
resolves only within its own resource's own `contained` list, and a count
> 1 (a duplicate id declared twice under one owner) never resolves either.
Reused ids under *different* owners resolve independently and correctly.

New fixture: `fhir_contained_scope/owner_scoped_contained.json` (valid
same-owner, invalid other-owner, duplicate-within-owner, missing target,
reused-id-under-a-different-owner — five resources in one bundle).

### Finding 4 — Unsupported Bundle resources disappeared silently

**Reproduced**: a Bundle containing only an unsupported `Organization`
resource returned `disposition: PROCESSED`, `record_count: 0`, no reason
code — read as a clean, fully-processed file.

**Fix**: `parse_fhir` now classifies every Bundle entry explicitly
(`FHIR_RESOURCE_TYPE_UNSUPPORTED_IN_BUNDLE`, `FHIR_ENTRY_MISSING_RESOURCE`,
`FHIR_ENTRY_MALFORMED`) into `FhirResult.held_resources: list[(ordinal,
reasons)]`, surfaced through `ingest.run_ingest` into the same
`IngestResult.held_records` list CSV malformed rows already use.
`resource_no` is now the **Bundle.entry ordinal itself** (not a compacted
counter that silently skips held entries), so ordinals stay meaningful.
Disposition policy: a Bundle with entries but **zero** supported resources
extracted is `HELD` with `FHIR_NO_SUPPORTED_RESOURCES_IN_BUNDLE` (not a
false-clean `PROCESSED`); a Bundle with *some* supported entries stays
`PROCESSED` but carries `FHIR_ENTRIES_HELD` plus the per-entry held reasons;
a genuinely empty `entry: []` Bundle stays cleanly `PROCESSED` with no
spurious hold. The safe report's `status` field now also turns
`HELD_PRESENT` when `ingest_result.held_records` is non-empty even if no
*file's* disposition itself is HELD (a held CSV *row*/FHIR *entry* inside
an otherwise-PROCESSED file was not previously reflected in the top-level
status — a one-line consistency fix in the same spirit).

New fixtures: `fhir_unsupported_entries/{unsupported_only_bundle,
mixed_supported_unsupported_bundle, supported_empty_bundle}.json`.

### Finding 5 — Quality evaluation did not measure the promised metrics

**Reproduced**: `scripts/eval_gate1.py`'s `_match` helper used substring
*containment* for "overlap", not real source-span intersection; entity
recall had no precision/F1/FP counting at all; `link_metrics` indexed
records by `file_path` alone, silently overwriting one of several rows/
resources from the same file (e.g. `household_shared/family.csv`'s two
rows collapsed to one, meaning the `GOLD_NON_LINKS` entry referencing
`"household_shared/family.csv:0"` / `":1"` never matched any real record —
the row-specific negative check was checking nothing); a gold cluster
counted "fully linked" after filtering to ACCEPTED-only records, so a
group missing 3 of 4 expected records could still read as `len==1` and
pass; the alias-only-vs-full "ablation" filtered evidence tiers out of one
single merged detection run, never actually running detection with the
gazetteer/cue routes disabled.

**Fix** (`scripts/eval_gate1.py` fully rewritten):
- `GoldSpan` carries real source coordinates (`file_path`, `record_no`,
  `role`, and either `(0, len(text))` for a structured field or
  independently-verified `char_start`/`char_end` for free text — located
  directly in the raw fixture text, never derived from the detector's own
  output, to avoid circularity).
- `entity_metrics` does one-to-one bipartite-style matching (a predicted
  span is consumed by at most one gold span; exact match preferred over
  overlap) and reports real `true_positives_exact/overlap`,
  `false_negatives`, `false_positives_in_annotated_scope`, precision,
  recall (exact and overlap, reported separately), and F1 — stratified by
  language and structured/free-text.
- **Precision is scoped to `FULLY_ANNOTATED_SCOPES`** — `(file_path, role)`
  pairs this repo has exhaustively labelled — and a **runtime self-check**
  asserts `len(gold) == len(detected)` for every such pair on every run;
  if that ever drifts (a detector change adds/removes a real span nobody
  re-labelled), the eval run fails loudly instead of silently mis-scoring
  precision. (The self-check is bypassable with `strict=False`, used only
  by the evaluator's own synthetic unit tests in
  `tests/test_eval_gate1.py`, which deliberately construct a mismatch to
  exercise the precision math itself.)
- `link_metrics` resolves every gold spec through the record's own
  globally-unique `record_key` (never `file_path` alone); a spec is either
  a bare `file_path` (exactly one record expected) or `"file_path#N"` for a
  specific row/resource in a multi-record file. A group counts
  `fully_linked` only when **every** expected record is present *and*
  `ACCEPTED` *and* they share exactly one cluster id — not "the ones that
  happened to be accepted agree." Added genuine pairwise link
  precision/recall (`pairwise_true_positive_links`, `pairwise_missed_links`,
  `pairwise_false_merges_sampled_negatives` — explicitly documented as
  computed over the *sampled* hard-negative pairs, not an exhaustive
  negative label set) alongside the whole-group metric.
- `detect.names.detect_free_text_names` gained an `enabled_routes:
  frozenset[str]` parameter (default: all three routes — no behavior
  change), threaded through `detect_in_text` and `plan.run_pipeline` as
  `enabled_name_routes`. `alias_vs_full_ablation` now runs **two fully
  independent `run_pipeline` passes** (`{"alias"}` vs. the default) over
  the same note set and measures real recall on each — an actual
  detector ablation, not a post-hoc filter.
- Added `candidate_recall`: checks whether each gold positive pair was even
  available to the scorer (present in the fuzzy-blocking candidate pool or
  an exact scoped-identifier match) *before* thresholding — a genuinely
  different question from whether the pair was ultimately accepted.
- `tests/test_eval_gate1.py` (new, 10 tests): the evaluator's own
  regression suite — injected FP decreases precision, a removed true span
  decreases recall, a shifted boundary diverges exact from overlap,
  repeated identical text in different records is not cross-satisfied, one
  predicted span cannot satisfy two gold spans, a merged pair of patients
  decreases pairwise precision, a split patient decreases pairwise recall,
  omitting one group record fails "fully linked," and two CSV rows in one
  file are independently resolved (the literal original bug).
- One genuine, now-fixed boundary issue surfaced while rebuilding the gold
  set: the held-out gold label `"Smt. Kalawati"` expected the honorific
  *in* the span, but `detect.names._HONORIFIC_PREFIX_CUES` deliberately
  excludes a pure title (`Shri`/`Shree`/`Smt.`) from the name span — by the
  same design already applied to `"Dr."` (provider names). The gold label
  was wrong, not the detector; it is now `"Kalawati"`, and held-out exact
  recall is genuinely **1.000** (the "span-boundary miss" previously
  reported in §8 was an artifact of a bad gold label, not a real limitation).

## 2b. Two additional findings reported after the initial repair

These were reported in a follow-up review of the repair itself (one a
regression the Finding 1 fix introduced; the other a pre-existing defect
the camelCase fix below happened to expose). Both reproduced first, then
fixed, same discipline as §2.

### Raw filename leaking into the safe report

**Reproduced**: two CSV rows sharing a UHID value, in an unconfigured file
named `SYNTHETIC_CANARY_PATIENT_9988776655.csv`, produced the exact-match
reason code `"SCOPED_REF:UNKNOWN_SOURCE:SYNTHETIC_CANARY_PATIENT_9988776655.csv:uhid"`.
That reason code is tallied into the **safe** report
(`linking.reason_code_tally`), so the raw filename leaked into public
output — a regression introduced by Finding 1's own fix (the per-file
`UNKNOWN_SOURCE:<path>` fallback issuer was being used verbatim as the
public label for every exact scoped match, not just an internal key).

**Fix**: `identity.scoped._public_scope_label(key)` replaces the dynamic
`f"{issuer}:{scheme}"` label with a **fixed, bounded** one: a `kind` drawn
from `{"NATIONAL_ID", "UNKNOWN_SOURCE", "CONFIGURED_SOURCE"}` plus a scheme
name only when it's drawn from the fixed, known header-alias vocabulary
(`HEADER_ALIASES` + `"fhir_identifier"`) — never the raw issuer string
(file path, facility-field content, FHIR `identifier.system` URL, or even
an operator-configured `--source-system` name), and never an arbitrary
scheme string (a FHIR system URL used as scheme falls back to `"OTHER"`).
The underlying `ScopeKey` used for actual matching is unchanged — only the
*label* surfaced through `reason_codes` (which flows into both artifacts)
is sanitized. Gate 1's canary check (`_check_no_canary_leak`) now plants a
**second** canary purely in a filename (not field content) and asserts it
never reaches the safe report either; `tests/test_identity.py::
test_raw_filename_does_not_leak_into_safe_report_via_a_reason_code`
reproduces the exact scenario directly.

### CamelCase/PascalCase name fields lost structured detection

**Reproduced**: `{"patientName": "Zevqori Alqaven"}` (an unfamiliar name:
not in the gazetteer, no honorific/relation cue) produced **zero**
detections. `header_aliases.normalize_header` lowercased and replaced
underscores but never split a camelCase boundary, so `"patientName"`
normalized to `"patientname"` — which matches no alias (the alias is
`"patient name"`, with a space). The field's role fell through to `OTHER`,
routing it through free-text detection, whose gazetteer/cue routes have no
way to catch a name they have never seen and that carries no honorific —
exactly the case a structured, header-anchored field is supposed to
guarantee retention for regardless of familiarity.

**Fix**: `header_aliases._CAMEL_BOUNDARY` (a lowercase/digit-to-uppercase
lookaround) splits `"patientName"`/`"PatientName"` into `"patient Name"`
before the existing lowercase/underscore normalization, so both forms
normalize identically to `"patient name"` and resolve correctly — including
through nested JSON paths, since role resolution already operates on the
path's last dotted segment. Verified with an **unfamiliar** name (no
gazetteer/cue dependency), a nested field (`visit.doctorName`), and the
resulting source coordinates (the whole field value, offset 0, as any
other structured field).

While fixing this, a second, related defect surfaced: `json_adapter`'s
key-inspection pass (which deliberately re-runs detection on a JSON key's
own text, to catch content accidentally used as a key, e.g.
`{"Mohammad Arif": "..."}`) was *also* resolving a known schema key's own
role via the header-alias lookup — so once `"patientName"` started
resolving correctly, the **key string `"patientName"` itself** became a
spurious `PATIENT_NAME` feature (text `"patientName"`, not a real name),
which would have fed a bogus token into `identity.build_candidate_features`'s
name-token list for every `patientName`-keyed JSON record. A key's own role
is now always `OTHER` regardless of whether its text matches a known alias
— it is still inspected via free-text detection (gazetteer/cue) exactly
like any other unexpected key text, which is the only thing that check was
ever meant to catch. `tests/test_ingest_adapters.py` gained 6 regression
tests for both the fix and this follow-on correction; `scripts/
eval_gate1.py`'s gold set for the two Devanagari consultation-JSON fixtures
was updated to match the now-correct single whole-field span (previously
fragmented into per-token free-text spans, a side effect of the same
camelCase gap, not a separate decision).

## 3. Gate 1 strengthened against vacuous success (Task 6)

`gate.phase1._check_corroborated_links` and `_check_hard_negatives`
previously filtered to `ACCEPTED`-only records before checking the result,
so an empty/partial accepted set could pass vacuously (a missing fixture,
or 3 of 4 expected records silently lost to HELD, both read as success).

- New `_fully_linked_group(private, path, expected_count)`: requires the
  **exact expected record count**, **all** `ACCEPTED`, and exactly one
  shared cluster id.
- New `_require_records`/explicit presence checks in `_check_hard_negatives`:
  every hard-negative fixture's actual record count is asserted before any
  merge check runs; a missing fixture now fails loudly instead of the
  merge check trivially passing over an empty comparison.
- Four new Gate 1 checks wire the new source-scope/FHIR regression fixtures
  into the gate itself: `source_scope_regression`,
  `fhir_subject_reference_regression`, `fhir_contained_scope_regression`,
  `fhir_unsupported_entries_regression`.
- `tests/test_gate.py` gained 6 direct unit tests proving the strengthened
  checks actually catch regressions (partial group, missing fixture, a real
  incorrect merge, an arbitrarily-resolved ambiguous FHIR reference) —
  fault-injection in the same spirit as the existing
  `test_gate_fails_loudly_when_a_check_is_broken`.
